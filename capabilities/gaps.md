# 能力缺口清单 · Capability Gaps（应有但缺失/不全 → 增强引导）

> 记录**应当有、但当前缺失或不全**的跨库能力（缺口 backlog）。
> **核心目的**：让玩家/系统/后续接替者知道——"还有这些能力可以去获取/增强"，
> 而不是因为当前没有就以为"不存在这个机制"。每个缺口都给出**建议获取路径/增强引导**。

> 状态字段：`待获取`(有建议去向，未接入) / `建设中`(已启动，未完成) / `部分可用`(有部分能力，不全)。
> 登记字段见 [registry.md](registry.md)；本清单是 **registry.md 中"缺口"项的展开台账**。

## 一、分派/路由缺口（秘书机制）

### G1｜`cap.mishu.route` 秘书·接待路由 — 待获取
- **应当有**：遇到不确定诉求，先路由给"秘书·接待"由它判断该交给谁，而不是全抛人工。
- **当前缺在哪**：秘书团（`dongdongxiaozu/zhuanyemishutuan`）在 CNB NPC 生态中存在，但本仓库**尚未接入可被唤醒来分派的实例**。
- **为什么重要**：这是"自动化决策体系"的关键一环——把"要不要问人工"也变成机制。
- **获取/增强引导**：
  - 在 Issue 召唤 `@dongdongxiaozu/zhuanyemishutuan(秘书·接待)` 验证能否被唤醒；
  - 若能 → 把未知路由的默认动作改成"先 @ 接待"；若不能 → 联系秘书团 owner 开通本仓接入权。
  - **完成判定**：未知诉求不再回抛人工，而是先被接待承接分流。

### G2｜`cap.mishu.assign` 秘书·分派编排 — 待获取
- **应当有**：接待判断后，由秘书长转派对应角色（秘书/经理/总师），中间无"问人"断点。
- **当前缺在哪**：分派目前仍靠经理在 Issue 手动 @ 触发，未自动化。
- **获取/增强引导**：同 G1——接入秘书团后，把"分派编排"接到接待之后，形成 `接待→分派→执行` 自动化链路。

### G3｜`cap.mishu.session` 秘书·会话/状态管理 — 待获取
- **应当有**：跨会话保持状态与上下文，避免"换库/换会话机制就丢"。
- **当前缺在哪**：本仓库机制绑定在单库上下文，换会话/换库易失。
- **获取/增强引导**：纳入秘书团"会话/状态管理"能力；本仓库侧把关键机制（本能力注册表即其一）落到仓库内持久文件，做到"机制跟库走，不跟会话走"。

## 二、评分/换算缺口（LanceDB 后端）

### G4｜`cap.score.db-lancedb` LanceDB 双库读写 — 部分可用
- **应当有**：score-engine 能读写 LanceDB 双库（换算库+分析库）。
- **当前缺在哪**：代码路径存在，但**运行环境缺 `lancedb` 第三方依赖**，CI/本地无该包时退化纯标准库 JSON 表兜底（API 一致但非真正向量库）。
- **为什么重要**：蓝图指向 LanceDB 向量检索，当前退化仅够功能演示。
- **获取/增强引导**：在目标环境安装 `lancedb`（`pip install lancedb`）→ 用 `--backend lancedb seed` 真正灌入向量库。
- **完成判定**：`score_engine.cli db --backend lancedb seed` 本地跑通且非 JSON 兜底。

## 三、检索/图谱缺口（蓝图演进）

### G5｜`cap.graph.layer` 14层知识图谱 — 建设中
- **应当有**：把题目/知识点组织成 L0~L13 目的驱动知识图谱（由架构·总师蓝图定义）。
- **当前进展**：**L0→L1→L2 主链已落地**（见 `graph/` + `scripts/graph.mjs`）：L0 最小知识点、L1 题目、L2 使用场景已结构化，函数硬通道 `covered_by`/`requires` 可做层间跳转与精准刷题。
- **仍缺在哪**：L3~L13（人类分类/章节/交叉题/标准等）高层节点尚未建模。
- **获取/增强引导**：沿用 `graph/graph-seed.json` 的 schema 继续往 L3~L13 扩节点，再接高层关系。

### G6｜`cap.graph.vector` LanceDB 向量检索 — 待获取
- **应当有**：对知识点/题干/场景做向量化语义检索（多向量加权排序）。
- **当前缺在哪**：未建向量库、无 embedding 模型接入。
- **获取/增强引导**：待 G4(LanceDB) 与 embedding 选型（本地开源 vs API）拍板后建向量库。

### G7｜`cap.graph.func` 函数+向量层间跳转 — 部分可用
- **应当有**：层间双通道跳转（向量软通道 top-K + 函数硬通道 relations 关系表）。
- **当前进展（函数硬通道已通）**：`graph/graph-seed.json` 的 `relations` + 题目 `知识点` 字段已建立 `requires`/`covered_by`，`node scripts/graph.mjs` 可做 L0→L1→L2 精确跳转（`by-scene`/`by-kp`/`jump`/`scene-from-kp`）。
- **仍缺在哪**：**向量软通道**未接——语义 top-K 检索需 LanceDB 依赖（G4）+ embedding 选型就绪后才能启用。
- **获取/增强引导**：先补 G4(LanceDB) 与 embedding，再在 `graph.mjs` 加向量检索分支，与函数跳转合并为双通道。

## 四、如何驱动缺口收口
- 本清单**随机制推进实时更新**：某缺口一旦接入/建好 → 移到 [registry.md](registry.md) 标记 `可用`，从本清单移除或标"已获取"。
- 需要"引导玩家/系统去增强"时：直接引用本清单对应 G# 项，提供明确去向，避免"不知道有这个机制"。
