# 跨库能力注册与索引机制 · Capability Registry

> 把本仓库**可能需要调用的跨库能力**，提前写成**可查、解耦、可缺口跟踪**的能力契约目录。
> 目的：让"能力"在云端就该有地址、可被调用，而不是只到本地拉取时才有；让"缺什么能力、可以去哪增强"一目了然，不靠玩家/系统自己猜。

---

## 一、机制要解决的两个问题

### ① 跨库机制"像丢了一样"
之前在别的库定好的机制（秘书路由 / 角色触发 / 白名单 / 验收口径…）一旦换库就像消失，
因为机制**绑定在某个库的上下文**里。解法：把**跨库通用能力**收敛登记到这里，作为"能力契约"，
业务库只需**声明"我要调用哪个能力"**，能力源在别处也能被索引、被唤醒，不再"丢"。

### ② 该有的能力不全 / 玩家不知道可以去增强
有些能力"应当有"，但当前因为资源不全 / 无对应源而不可用。
若只有可用的能力登记，玩家/系统**根本不知道"还可以增强"**。解法：登记时**显式区分可用/缺口**，
把"应有无源"的能力记成缺口，附**获取/增强引导**，让想去增强的人有明确入口。

---

## 二、三个核心原则

| 原则 | 含义 |
|------|------|
| **① 解耦登记** | 这里只登记能力的**契约**（代码/名/来源/调用方式/状态），**不内嵌实现**。实现留在各自能力库。 |
| **② 有源即用，无源即缺** | 有能力源 → 按契约自动匹配、可调用；无能力源 → 不阻塞、不硬编，标记"缺口/待获取"。 |
| **③ 缺口留痕 + 引导** | "应当有但不全"的能力必须被记录（registry 状态=gap / gaps 清单），并给出**获取/增强引导**，让人知道"有这种机制、可以去增强"。 |

---

## 三、目录结构

| 文件 | 内容 |
|------|------|
| `capabilities/registry.md` | **能力注册表（索引）**：所有已登记能力契约，含可用/缺口状态、来源库、调用入口 |
| `capabilities/gaps.md` | **能力缺口清单**：应当有但当前缺失/不全的能力 + 获取/增强引导（gap backlog） |
| `capabilities/README.md` | 本机制说明（本文件） |

> 能力本身在各自的能力库，本目录**只做契约登记与索引**，不拷贝实现 → 解耦。

---

## 四、能力契约字段（registry.md 每项登记字段）

| 字段 | 必填 | 说明 |
|------|------|------|
| 能力代码 | ✅ | 全局唯一的 machine 标识，如 `cap.mishu.route` |
| 能力名 | ✅ | 人读名 |
| 所属域 | ✅ | 归类域（分派/评分/协作/检索…） |
| 能力类型 | ✅ | `本地内置`(本仓库自产) / `跨库调用`(调他库) / `缺口`(应有无源) |
| 来源库 | 条件 | 能力定义所在仓库/地址（跨库调用必填；缺口填"待获取→建议去向"） |
| 调用入口 | 条件 | 如何调用：skill 名 / 命令 / @角色触发 / API（跨库调用与本地内置填） |
| 能力状态 | ✅ | `可用`(有源可调) / `缺口`(应有无源/不全) |
| owner | ✅ | 能力维护方 / 缺口跟踪方 |
| 登记时间 | ✅ | 首次登记日期 |
| 说明 | 建议 | 一句话描述 + 已知局限 |

## 五、调用匹配规则（有源即用 / 无源即缺 / 缺口引导）

```text
需要"某个能力"时：
  ① 查 registry.md：该能力代码是否已登记？
     ├─ 已登记且状态=可用 → 按「来源库 + 调用入口」自动匹配、执行调用 ✅
     └─ 已登记且状态=缺口，或未登记 →
  ② 判定"应当有"（该能力属于本业务目标所需的通用能力）：
     ├─ 是 → 在 registry.md 登记/补登该能力，状态=缺口，
            并写进 gaps.md（附获取/增强引导）→ 让想增强的人有入口 📌
     └─ 否 → 记录为"暂无必要"（不强行造），不算缺口
```

**关键**：能力只做**契约登记**，不把实现绑进本库。
**可调** = 本库声明能用 + 来源库实际存在 → 自动匹配调用；
**不可调** = 无来源 / 来源不全 → 记为缺口并给引导，而不是"静默消失 / 玩家不知道"。

---

## 六、登记 / 更新流程（保持"防挡也防乱"）

1. **新增/变更能力**：PR 改 `registry.md`（或 `gaps.md`），登记 owner + 登记时间 + 变更历史。
2. **状态流转**：某能力从缺口 → 有源可用时，更新 `registry.md` 状态为 `可用`、填来源库，并从 `gaps.md` 移除/标注已获取。
3. **删除能力**：PR 移除登记并说明迁移路径，禁止静默删除。
4. **校验**：注册表保持字段完整、能力代码唯一（人工走读 + 评审即可，轻量不建脚本）。
